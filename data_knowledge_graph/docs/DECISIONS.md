## 决策点 1 —— 源实体抽取方法

**建议默认方案（原文）**：用数据集自带话题实体或根实体

**落地做法**

| 数据集 | 做法 | 覆盖率（WebQSP test 300 / CWQ dev 300） |
|---|---|---|
| WebQSP | 直接用 `Parses[i].TopicEntityName`（官方标注） | 285/300 用标注；13 例因名字不在子图而改用链接；**99.3% 落在 KG 中** |
| CWQ | 官方 JSON **没有** `topicEntityMid`，只能链接：问题文本对 257 万实体词表做最长匹配，候选再由"黄金关系链能否走到答案"校验 | 100% 落在 KG 中（链接 + 校验） |

**为什么 CWQ 不能照抄 WebQSP**

CWQ 官方 release 的字段只有
`ID / answers / composition_answer / compositionality_type / created / machine_question /
question / sparql / webqsp_ID / webqsp_question`——既没有 `topicEntityMid`，也没有 `sexpr`
`webqsp_ID` 指向的是**组合前**的原问题，组合后的实体（例如 Azad Kashmir）不在里面，
所以只能靠链接 + 黄金链校验

**风险与缓解**
* 链接可能选错实体 → 用"链能走到答案"做硬校验，错选基本会被拒（`match_method` 会退化成`relaxed_order` 或 `none`，可统计）
* 同一个问题可能有多个实体提及 → 按"最长提及优先"，并让 `mid2name` 交叉校验常量名字
  （`m.060c4` 的官方名字是 `President`，那提及 `The President` 直接判为不一致）

**状态**：已确定，代码在 `fog/naming.py` + `fog/pipeline.py:resolve_example`

## 决策点 2 —— mid 到文本映射与无名实体回退

**建议默认方案（原文）**：`type.object.name` 取英文名，无则用 mid。

**落地做法**

* 子图侧本来就已经是"名字空间"：RoG 预处理把 mid 换成了 `type.object.name`，换不到的地方就保留 mid。所以**回退到 mid 是这套图的既有约定**，A 只是沿用
* 标注侧（mid 空间 → 名字空间）需要一张 mid→name 表。A 不依赖 30 GB 的 Freebase 转储，而是**从标注自己身上收集**：WebQSP 的 `TopicEntityName` / `Answers[].EntityName` /`Constraints[].EntityName`，CWQ 的 `answers[].answer_id → answers[].answer`产出 `data/interim/mid2name.json`，**40,109 条**，覆盖了链两端所有"有名字的实体"
* 中间实体（CVT）本来就无名字，在 KG 里就是 mid 形态，天然对齐

**为什么这样就够**
黄金链上"有英文名的节点"只有三类：源实体、答案实体、约束实体——三者的名字标注里都有
其余中间节点几乎都是 CVT（`m.0h89drz` 这类），KG 里存的就是 mid，不需要映射

**状态**：已确定，代码在 `fog/naming.py:MidNameResolver`

## 决策点 3 —— 黄金路径转换规则

**建议默认方案（原文）**：由 WebQSP SPARQL 或 CWQ S-expression 反推。

**落地做法**（两步）

1. **mid 空间求关系链**：解析 SPARQL 图模式（剔除 `FILTER(...)` 与 `EXISTS{...}`），
   在模式图上求"源常量 → SELECT 变量"的最短路径，得到带方向的关系步序列
   WebQSP 另外直接采用官方 `InferentialChain`（最权威）
2. **名字空间对齐**：按关系链在 KG 上逐跳游走，只接受**终点命中答案**的路径
   方向不一致时允许反向（记为 `relaxed`）；仍失败则用"关系集受限的最短路"（`relaxed_order`）

**关于 S-expression**：官方 CWQ JSON 里没有 `sexpr` 字段（见决策点 1），所以生产管线对两个
数据集统一走 SPARQL。S-expression 解析器已在 `fog/gold/sexpr.py` 实现并单测，
拿到带 sexpr 的版本可直接切

**对齐结果**

| 数据集（300 题） | 成功对齐 | 仅链走通(exact) | 反向放宽 | 关系集受限 | 失败主因 |
|---|---|---|---|---|---|
| WebQSP test（300 抽样） | **93.3%** | 93.0% | 少量 | 0.7% | 答案不在子图 2.7%、链走不通 3.3% |
| CWQ dev（300 抽样） | **85.7%** | 83.0% | 少量 | 2.7% | 关系链在子图里断掉 14.3% |
| WebQSP test（全量 1,639） | **92.9%** | — | — | — | — |
| CWQ dev（全量 3,519） | **83.3%** | — | — | — | — |

失败根因**不是转换规则**，而是"RoG 检索子图本身不含这条路径"（子图是检索结果的并集，
不是全量 Freebase）。因此这不是能靠改规则修复的损失，属于数据来源的硬约束

**状态**：已确定，代码在 `fog/gold/sparql.py` + `fog/gold/matcher.py`

## 决策点 7 —— 极高度数通用关系的过滤阈值

**建议默认方案（原文）**：度数大于 1000 过滤。

**实测结论：这条建议的"1000"只能用在实体度数上，不能用在关系频次上。**

本子图共 8,258,891 条三元组、7,042 个关系。按**关系频次**卡 1000：

| 阈值 | 保留关系数 | 保留三元组 | 占比 | 3 跳后黄金边召回 |
|---|---|---|---|---|
| ≤100 | 4,957 | 86,941 | 1.05% | — |
| ≤1,000 | 6,345 | 552,951 | 6.70% | **5.8%** |
| ≤10,000 | 6,892 | 2,436,604 | 29.5% | 27.6% |
| ≤100,000 | 7,027 | 5,767,506 | 69.8% | 58.6% |
| ≤200,000 | 7,040 | 7,654,598 | 92.7% | 70.1% |
| 不限制 | 7,042 | 8,258,891 | 100% | 70.1% |

按**实体度数**卡 1000 时只影响 614 个枢纽实体（United States of America 136,247 度、
Male 121,644 度、English Language 58,542 度……），正好是候选爆炸的来源。但一刀切
"枢纽不展开"会把**黄金路径穿过枢纽**的题一起剪掉

**网格校准**（WebQSP test 等距抽样 200 题，其中 180 题黄金路径可对齐；
`scripts/capcheck.py`，结果在 `reports/stats/capcheck_webqsp_test.json`）：

| 旋钮 | 取值 | 黄金边召回 | 全召回 | 平均边数 | 单题耗时 |
|---|---|---:|---:|---:|---:|
| `max_edges` | 10,000 | 85.5% | 77.8% | 9,227 | 0.23 s |
| | 20,000 | 88.4% | 83.9% | 18,403 | 0.24 s |
| | 40,000 | 90.1% | 87.2% | 36,523 | 0.28 s |
| | 80,000 | 90.9% | 88.9% | 72,039 | 0.36 s |
| `node_degree_max` | 2,000 | 80.1% | 76.7% | 16,057 | 0.19 s |
| | 5,000 | 88.4% | 83.9% | 18,403 | 0.24 s |
| | 10,000 | 91.8% | 86.7% | 19,180 | 0.26 s |
| 组合 | (10k, 20k) | 91.8% | 86.7% | 19,180 | 0.26 s |
| | (10k, 40k) | 93.4% | 90.0% | 38,079 | 0.30 s |
| | **(20k, 40k)** | **95.1%** | **91.7%** | **38,746** | **0.35 s** |
| | (10k, 60k) | 94.0% | 91.1% | 56,883 | 0.43 s |

反直觉但可解释：`node_degree_max` 从 5,000 提到 20,000 召回涨 6.7 个点，但**完全不限制**
反而更差（90.2%）——20k 节点预算被枢纽的一跳邻居吃光，2–3 跳的有用节点挤不进来

**最终取值**（`fog/subgraph.py:SubgraphConfig` 默认值 + `configs/*.json`）

| 旋钮 | 取值 | 依据 |
|---|---|---|
| `node_degree_max` | **20,000** | 与 `max_edges=40k` 组合时抽样召回 95.1%（最高档）；全量 test 实测 94.1% |
| `max_edges` | **40,000** | 再翻倍只多 0.8 个点召回，体积翻倍 |
| `rel_degree_max` | **200,000** | 再低会损失 >10% 黄金边 |
| `rel_blocklist` | `common.topic.notable_types` / `freebase.valuenotation.*` / `common.webpage.*` / `type.object.*` | 元数据与类型断言，永远不是证据 |
| `max_nodes` | 20,000 | 与 `node_degree_max` 配合的成本上限 |
| `max_gather` | 2,000,000 | 单层邻居收集的硬上限，防枢纽把内存/耗时打爆 |

**状态**：已确定并被实测校准（`reports/stats/capcheck_webqsp_test.json`、
`reports/stats/expansion_webqsp_test.json`）。

## 决策点 8 —— 全量 Freebase 或子集

**建议默认方案（原文）**：先用源实体 3 跳子图。

**落地做法**：采用 **RoG 预处理子图的并集**作为"Freebase 子集"，而不是自己从 30 GB 转储
里抽 3 跳。理由：

1. 全量 Freebase 需要 Virtuoso + 约 100 GB 内存，本复现环境不具备；
2. RoG 子图并集是**真实 Freebase 三元组**，规模 8.26 M 条 / 257 万实体 / 7,042 关系，已经比"每题 3 跳"大得多，3 跳 BFS 在其上完全可行；
3. 下游拿到的是同一套名字空间，与文献里 ToG/RoG 的预处理完全同构，换全量 Freebase 时只需要换 `TripleIndex` 的数据源（`fog/kg/virtuoso.py` 已给出物化接口）

**代价（必须写进报告）**：子图召回有上限——黄金边召回率 **94.1%**（全量 WebQSP test）、
**89.3%**（CWQ dev）；黄金路径对齐率 92.9% / 83.3%。

**状态**：已确定
